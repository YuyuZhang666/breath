# v1.4.0 Stage 5 - Task and Treasure Baseline

Date: 2026-09-21

## Scope

This stage adds bounded TaskAgent anytime execution, reusable task SOPs, task abandonment cooldowns, structured treasure evidence, conservative treasure retries, dynamic purchase checks, and Phase 5 telemetry. The implementation is incremental and keeps the existing director, day planner, fortification planner, Phase 2.5 fire control, Phase 3 rollout, validator, fallback, and watchdog paths.

The real battle JSON is private and unavailable. Tests therefore use repository fixtures and synthetic observations. The observed treasure reward of 200 score and 100 gold is represented as `source='battle_log'`; it is not treated as an official fixed rule and can be injected or disabled.

## TaskAgent behavior

- ECONOMY and SCORE profiles can accept positive-value tasks; SURVIVE blocks new work but does not discard an already active task unless an emergency item action or twilight recall takes priority.
- LLM prompts and `executeCmd` are asynchronous and tied to the exact task fingerprint. Stale responses and unknown command results cannot be submitted as successful answers.
- Bounded candidates support an early valid submission followed by a distinct, higher-quality answer. Failed answers are excluded from the future quality threshold.
- SOP reuse is exact for identical tasks and prompt-assisted for structurally similar tasks. Empty legacy fingerprints are never used for direct answers.
- Abandoned task type/position pairs receive a 30-round local cooldown and are not immediately reacquired.
- Emergency compute mode still reconciles submission feedback and can learn a successful SOP.

## Treasure behavior

- Only structured JSON evidence is parsed. Free-form folklore is retained for observability but does not create a guessed candidate.
- Candidate, evidence, news, and result histories are bounded.
- The first attempt requires high confidence. Retry is disabled by default and, when explicitly enabled, requires evidence observed after the failed attempt plus a relevant position/day or item change.
- Duplicate JSON with different whitespace or key order does not count as new evidence.
- Purchase planning uses observed shop inventory/prices, backpack capacity, the director's dynamic gold reserve, and expected gold return. No fixed item list or fixed purchase cost is assumed.
- An ordinary day PREPOSITION move may be replaced by treasure work. Task actions, item use, controller assignments, and twilight recall remain protected.
- Same-match treasure state survives a forward round gap; round rollback or a changed static map signature starts a fresh state.
- Validator checks backpack contents and adjacency for summon, observed shop and aggregate gold for buy, inventory/shop adjacency for sell, inventory for use, and resource-zone adjacency for collect.

## Key interface changes

- `StrategyEngine(..., task_agent=..., treasure_agent=...)`
- `TaskAgent.reconcile(...)` and `TaskAgent.apply(...)`
- `TreasureAgent.reconcile(...)` and `TreasureAgent.apply(..., task_active=False)`
- `TaskAgentState`, `TaskSop`, `AnswerCandidate`, `TreasureState`, `TreasureCandidate`, and `TreasureReward`
- New telemetry: `task_ms`, `task_candidate_count`, `task_sop_hit`, `treasure_ms`, `treasure_candidate_count`, `treasure_attempted`, and `treasure_result`

## Preservation checks

- Opening construction, wall repair/rebuild, dynamic reserve, upgrade/heal evaluation, mining, and selling remain in the Phase 2 planner and its regression suite.
- Weapon level 2/3 legal multi-target validation remains covered.
- Controller assignment caching remains covered.
- HTTP/protocol serialization, validator, fallback, and watchdog tests remain green.
- Unknown or unconfirmed rules remain disabled unless a feature flag or injected capability enables them.

## Known limits

- No private production match log was used, so reward confidence, treasure result semantics, and folklore schema must continue to be treated as observed capabilities rather than official invariants.
- Treasure score is not converted into spendable gold. Purchase break-even uses only the configured expected gold reward; score remains a strategic selection signal.
