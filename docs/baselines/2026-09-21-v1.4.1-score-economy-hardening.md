# v1.4.1 Score and Economy Hardening

## Scope

This increment implements the highest-confidence changes from the post-Stage 6
review without replacing the existing planner:

- preserve the command-result trailer before classifying sandbox output;
- coordinate active night tasks with controller assignment and NightForecast;
- run the documented request through the real HTTP/controller/engine path;
- carry job utility into joint selection and reserve a wall job across moves;
- maintain a forecast-driven stone reserve for opening walls and rebuilds;
- learn deterministic market signals from official news and validate them
  against observed vendor prices;
- retain exact-turn and item-multiset treasure negative evidence;
- parse only explicit, fully specified prose treasure clues;
- rank tasks with explicit score, speed, gold, travel, and SOP-duration terms;
- reject wrong-answer feedback before learning a successful SOP.

## Safety behavior

An active night task first receives a forecast made with the pioneer excluded
from weapon control. SAFE/WATCH retains the pioneer for the task. CRITICAL,
LETHAL, missing forecast, or assignment failure pauses task output for that
turn and returns the pioneer to ordinary fire control. The task state is not
discarded and no abandonment cooldown is created.

Controller cache signatures include excluded role IDs. A phase-task
availability transition invalidates the incremental forecast.

The docs/request.txt fixture is posted to the real local HTTP server in the
acceptance suite. The response must be nonempty, schema-complete, stable on
duplicate requests, and finish inside the configured 3 second internal
decision budget. This validates the supported path; Python cannot safely
preempt an arbitrary blocking planner thread, so the hard external timeout
still depends on all production planner components honoring their cooperative
budgets.

## Wall and economy behavior

TacticalCandidate.utility carries Job.value into candidate ranking and joint
scoring. BUILD_WALL movement and build candidates share an exclusive job key,
preventing two workers from converging on the same gap while still allowing
two workers to collect the same tail-depleting mine.

The stone reserve is the maximum of minimum_wall_stock, forecast expected
wall losses times wall material cost, and missing critical walls times wall
material cost.

Reserve is assigned deterministically to workers nearest reachable gaps.
Selling exposes only excess stone, and missing walls no longer force more
stone mining when current builder inventory already meets the reserve.

Official-news market rules require an explicit mineral, an unambiguous supply
event, and an explicit duration. Ambiguous text remains UNKNOWN. Signals are
bounded and deduplicated; observed vendor prices update per-rule
correct/wrong counters. No LLM calls are used.

## Treasure and task behavior

Treasure result 2 records position plus exact attempt round and does not
invalidate a whole day. Result 3 records a normalized item multiset across
all candidates. Both ledgers are bounded at 64 entries; saturation disables
automatic attempts instead of evicting old failures. The 200 score / 100 gold
default remains labeled battle_log, not official.

Natural-language treasure parsing only materializes a candidate when exact
coordinates, an explicit item list, and explicit opening days are all
present. Directional or symbolic prose remains unresolved.

Task expected value uses completion probability times task score and the
official-form speed term, plus a small explicit gold value, minus travel
cost. Validated SOPs maintain a bounded success count and solve-round EWMA.
A legal submit action accompanied by official errorCode 2 is not learned as
success.
