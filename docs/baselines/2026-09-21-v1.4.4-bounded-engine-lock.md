# v1.4.4 Bounded engine lock wait

## Scope

This reliability increment closes the request-deadline gap around the
`StrategyEngine` global lock. It does not change strategy weights, build
order, task value, treasure policy, or night target selection.

Before this change, a request used `with self._lock` and could wait without a
deadline behind another request. Forecast and search watchdogs could not run
until after the lock was acquired, so lock contention could consume the full
platform response window.

## Deadline contract

Lock acquisition now shares the request's absolute compute deadline:

```text
lock wait <= remaining compute time - emergency reserve
```

With the production defaults, the lock wait stops no later than 2.5 seconds
after request start, preserving the final 500ms compute reserve and the
separate response margin. A lock timeout returns the bounded deadline
fallback immediately:

- at night, already-positioned ready weapons may use the v1.4.3 emergency
  direct-fire path;
- by day, the engine returns an empty legal decision without running night
  forecast or emergency-fire code;
- session, memory, market, director, task, treasure, and Phase 2/3 work is not
  started after the lock timeout;
- the engine rechecks the reserve after acquiring the lock and releases the
  lock before executing fallback work.

Emergency requests also skip reconciliation. A normal-budget retry can apply
the observation later; the emergency attempt never leaves a partial session
update.

## Telemetry

The turn record adds:

- `engine_lock_wait_ms`;
- `engine_lock_timed_out`;
- `deadline_stage`, with `none`, `engine_entry`, `engine_lock`, `post_lock`,
  or `strategy`.

An intentional lock cutoff remains `fallback_reason=deadline_low` and
`compute_governor_action=emergency_reserve`; it is not reported as a
watchdog hit.

## Verification

Deterministic tests cover the exact 2.5-second default timeout argument, a
real two-thread contended `RLock`, and the post-acquire reserve boundary. The
contention request returns emergency fire before its compute deadline, while
the lock holder completes after the test releases it.

Validation on Windows / Python 3.13:

| Check | Result |
| --- | ---: |
| Full suite | 496 tests passed |
| R1-R130 median | 35.92ms |
| R1-R130 P99 | 42.47ms |
| R1-R130 maximum | 43.58ms |
| Forecast modes | none x70, lightweight x60 |
| Fallbacks | normal x130 |
| Watchdogs / prevented timeouts | 0 / 0 |

The synthetic replay validates bounded code paths and response legality. It
does not replace a platform replay with real socket latency and evolving
combat state.
